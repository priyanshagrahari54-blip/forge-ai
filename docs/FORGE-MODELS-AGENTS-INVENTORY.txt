FORGE AI — AGENTS, MODELS & PROVIDER ECOSYSTEM INVENTORY
==========================================================

Purpose
-------
This document records the current Forge architecture for its specialist-agent
fleet, concrete public model-name reference, provider ecosystem, provider
links, routing and failover. It is intentionally honest: a model name in an
inventory is not automatically a live connection.

1. AGENT FLEET
--------------
Forge currently defines a 1000-slot logical specialist agent fleet.

Architecture:
- 33 domains
- 30 specialist capability families
- 990 deterministic domain/specialty combinations
- Additional numbered slots bring the fleet to 1000
- AgentSlot fields: name, role, domain, specialty, capabilities, priority
- Fleet mode: logical-routable-fleet
- Execution: delegated-to-configured-model-fabric

Important:
The 1000 agents are routing/specialization slots. They are NOT a claim that
Forge has 1000 independently hosted neural networks. Multiple specialist
agents can be backed by different models, the same model with different
instructions/tools, or different providers according to routing policy.

Implementation:
- forge/agents/fleet.py
- DEFAULT_AGENT_FLEET = build_fleet(1000)
- fleet_snapshot() exposes count/domains/specialties/execution mode

2. AGENT -> MODEL ROUTING
-------------------------
Forge now has a deterministic routing-contract layer between logical agents
and Model Fabric.

Flow:

AgentSlot
  -> domain/specialty routing requirements
  -> canonical capabilities
  -> ModelRequest
  -> Model Fabric
  -> verified/configured model
  -> provider connector
  -> execution

Implementation:
- forge/agents/routing.py
- AgentRouteSpec
- route_spec()
- model_request_for_agent()
- route_snapshot()

The routing layer does NOT invent a model name. Model Fabric remains the
authority for actual model selection, verification, policy and availability.

4. PROVIDER FAILOVER
--------------------
Forge has quota-aware provider failover infrastructure.

ProviderRuntime tracks:
- failures
- successes
- cooldown_until
- last_error
- last_reason

Retryable conditions include:
- rate_limited
- quota_exhausted
- unavailable
- timeout
- transient

The failover layer skips providers in local cooldown and tries another eligible
candidate. It does NOT bypass provider quotas or manufacture capacity.

Implementation:
- forge/orchestration/failover.py

7. CAPABILITY REALITY / HONEST STATUS
--------------------------------------
Forge uses explicit capability-truth states:
- LIVE
- READY
- CONFIGURED
- ARCHITECTURE
- SIMULATED
- MISSING
- BLOCKED
- ERROR

Configured does not automatically mean live. Provider/model availability must
be established through runtime evidence and health/configuration checks.

8. MODEL ARCHITECTURE
---------------------
The intended flow is:

User task
  -> Supervisor / Planner
  -> task decomposition
  -> specialist-agent routing
  -> Model Fabric
  -> provider/model selection
  -> health/quota checks
  -> execution
  -> tests/debugging/review
  -> checkpoint/rollback if required
  -> final artifact

A specialist agent is a logical worker identity. Model Fabric decides which
configured model/provider can perform the required capability.

9. MODEL CONNECTOR STRATEGY
---------------------------
One provider connector can support many concrete model IDs.

Examples:
- OpenAI connector -> gpt-5.6 family and future verified OpenAI IDs
- Anthropic connector -> Claude family
- Google connector -> Gemini family
- Mistral connector -> Mistral family
- DeepSeek connector -> DeepSeek family
- xAI connector -> Grok family
- Cohere connector -> Command/North/Embed/etc.
- Hugging Face connector -> dynamically discovered model IDs
- Ollama connector -> locally discovered model IDs

Therefore 1000 agents do NOT require 1000 plugins.

10. BACKGROUND / CONTINUOUS EXECUTION
-------------------------------------
Forge's server architecture is designed for persistent background work. Tasks
can continue server-side instead of depending on the browser remaining open.
The architecture includes durable task state, background dispatch/workers,
persistent events, checkpoints, retry/recovery paths and task controls.

The G560 should therefore act primarily as a thin client/control surface.
Heavy AI/model inference should be delegated to configured remote/local server
resources rather than assuming the G560 itself can run frontier-scale models.

11. AI CITY / LIVE ACTIVITY
---------------------------
The cockpit's AI City is intended to visualize actual Forge work. Activity
should be backed by real backend events/task state rather than animation being
used as proof that a model or agent is working.

12. RUNTIME MODEL DISCOVERY — NEXT STEP
---------------------------------------
For each provider Forge should support, where the provider API permits:

- list models
- get model metadata
- capabilities/modality
- context length
- maximum output
- pricing when available
- availability
- authentication state
- quota/rate-limit state
- health check
- safe verification probe
- deprecation state

Only after these checks should Model Fabric classify a model as configured,
reachable, verified or LIVE.

13. HONESTY RULE
---------------
Forge must never claim that a model, provider, agent, tool, or capability is
LIVE merely because its name exists in a registry or catalog.

Registry entry != installed model
Public model name != API access
Configured != reachable
Reachable != successful inference
Architecture != implementation
Simulation != real capability

--------------------------
The architecture now has:
